# Backlog：明确不做的事，以及「如果要做会怎么做」

> 与 [需求与验收](01-requirements.md#五明确不做) 的分工：那份文档回答「**为什么不做**」（取舍的判断）；本文回答「**如果非做不可，路径是什么、什么信号出现才该做**」（前瞻的判断）。
> 两者合起来构成面试里「你知道边界在哪、也想过怎么扩展边界」的完整证据。**没有一条是拍脑袋拒绝的。**

图例：**触发条件** = 什么信号出现时这个「不做」应该被重新评估；**成本档** = 如果要做，工作量级别。

---

## 一、地基已就位、随时可启动（低成本）

这几项不是「不做」，是「刻意押后」——它们依赖的前置件已经在主干里，接上就是完整功能。

### 1.1 token 计价 → 预算护栏覆盖「部分超支」
- **现状**：预算护栏 `applyBudget` 已上线，但 `runs.cost_cny` 恒为 0（未接价格表），所以只有 `DAILY_BUDGET_CNY=0` 能触发降级；「今天花了 15 / 预算 20」检测不到
- **如果要做**：接一张 `{model → ¥/千token}` 常量表（火山/DeepSeek 各一行），`callLlm` 返回时按 `inputTokens/outputTokens` 折算，写入 `runs.cost_cny` —— **一行改动激活整套已就位的降级逻辑**
- **成本档**：1-2 小时 · **触发条件**：真实部署给非自己用、或要把「日均成本」写进产品指标时

### 1.2 结果缓存（AST 语义指纹做键）
- **现状**：语义指纹 `semanticFingerprint` 已上线（原为防震荡），它天然是「一条 SQL 的语义身份」
- **如果要做**：建 `sql_result_cache(key=指纹, columns, rows, as_of, built_at)`，执行前先查；命中即跳过 worker。因为指纹是语义级的，条件换序/别名互换的等价 SQL 自动命中同一份缓存
- **成本档**：半天 · **触发条件**：出现「同一批报表高频重跑」的真实负载时（注意：与报表固化 5G 有重叠，先确认固化解不了再上缓存）

### 1.3 回执扩展：R3 / R5 口径亮明
- **现状**：回执只翻译 R1（已完成）+ 时间范围；lint 其实已经认识 R3（COUNT DISTINCT）和 R5（毛利公式）的 AST 形状
- **如果要做**：把 lint 的识别逻辑抽成共享判定 → 回执按「lint 要求说明的范围 = 回执能翻译的范围」对齐加两行（「订单数已按订单去重」「毛利 =（成交价−成本）×数量」）
- **成本档**：半天 · **触发条件**：用户反馈「看不懂毛利/客单价数字的口径」时

### 1.4 CI 夜间全量重录
- **现状**：cassette 手工 `record` 模式重录；CI 只做 replay 门禁（零成本零密钥）
- **如果要做**：加一条定时 workflow（`schedule:`），带密钥跑 record 模式重录全 30 题 → 检测「模型行为是否漂移」，但**不自动提交**（漂移要人判断是有意义改进还是退化）
- **成本档**：2 小时 · **触发条件**：上游模型版本变更频繁、需要监控「静默退化」时

## 二、更大的方向：如果做会怎么做（当前明确押后）

### 2.1 真·多轮会话（指代消解 / 追问）
- **为什么现在不做**：把评测从「无状态单轮」变成「有状态」——会话记忆会摧毁「同一题两次跑出同一结果」的可复现性，而那是整个评测体系的命根（见 06-evaluation）
- **地基已留**：`/api/chat` 契约里 `conversationId` 字段从第一天就在（现在恒传 null），加会话是「填坑」不是「改契约」
- **如果要做**：① 建 `conversations` 表、`runs.conversation_id` 外键；② loop 开头读会话上下文注入 prompt（如上一问选中的口径、实体）；③ 前端从单答视图改聊天线程；④ **评测另起一套多轮题集**（带「追问→是否正确消解指代」的判分标准），与单轮 30 题并列，互不污染
- **成本档**：数天（含评测扩展）· **触发条件**：出现「那上个月呢？」「对比一下」这类真实追问需求，或作为作品集要展示「会话化能力」时——但必须连着第④步一起做，否则评测叙事断裂

### 2.2 完整语义层（QueryPlan IR + 确定性 SQL 编译器）
- **为什么不做**：它会通向另一个项目——从「取数 agent」变成「BI 引擎」，工作量以月计而面试几乎零加分（面试官要的是「你把 agent 做通了」，不是「你重造了 dbt metrics」）
- **如果要做**：把 8 条口径规则升级为一个声明式指标注册表（metric → SQL 片段的组合代数），agent 不再「写」SQL 而是「选」指标 + 填槽位；guard/lint 退化为组合校验
- **成本档**：数周 · **触发条件**：口径规则从 8 条涨到 50+ 条、手工 AST 检查维护不住时（信号：误报率红线频繁被触碰、新规则加不进去）

### 2.3 连接用户自己的数据库（多数据源）
- **为什么不做**：一旦开口子就要背下 DSN 凭据加密（AES-GCM）、SSRF 与 DNS rebinding 防护、连接池、方言差异（SQLite 的 `setAuthorizer`/EQP 优势在 PG/MySQL 上全部要重做）——安全叙事会从「九层」变成「无边界的攻击面」
- **如果要做**：先做只读 + 白名单表 + 服务端集中配置（不给用户填 DSN 的 UI），把「任意连接」这个最危险的口子留到最后
- **成本档**：数周 · **触发条件**：明确有第二个真实用户、且其数据不在 SQLite 里

### 2.4 智能洞察 / 预测（「为什么这个月下降了」）
- **为什么不做**：当前技术栈下最容易吹牛、也最容易被戳穿的部分——归因和预测需要的是统计/ML 能力，不是 LLM 写 SQL；用 LLM「讲故事」假装归因，违背本项目「每个数字可复核」的立身之本
- **如果要做**：先做**确定性的**归因组件（维度下钻找贡献最大的分组），LLM 只负责把确定性结果翻译成人话，绝不让它自己「推理」原因
- **成本档**：数天起 · **触发条件**：产品明确要往「分析」而非「取数」走时（那其实是下一个项目）

### 2.5 向量检索（few-shot / schema 召回）
- **为什么不做**：向量召回的 top-k 会随 embedding 模型版本、数据微调漂移——同一道评测题两次跑出**不同上下文**，准确率变化再也分不清是优化还是抖动，直接摧毁评测（这条与 4 张表的规模无关，是原则问题）
- **如果一定要做**（比如表涨到 300 张、关键词裁剪不够用）：用**版本冻结的 embedding 快照** + **固定 top-k + 确定性 tie-break**，并把召回结果作为一个可 A/B 的独立上下文层纳入评测（开关化，像 FEW_SHOT/ENUM_INJECTION 那样能 on/off 对比）
- **成本档**：数天 · **触发条件**：真实表数量让关键词+外键闭包的裁剪精度明显不够（信号：schema 卡片漏掉必要事实表的错题上升）

## 三、已被实测证伪、永久绕开（技术选型层面）

这些不是「不想做」，是「试过或查过，证明做不到或前提不成立」——保留在此作为决策留痕，避免未来重蹈：

- **`better-sqlite3` + `db.interrupt()`**：13.0.3 无 `interrupt` 方法；且 db 句柄归 worker、主线程调不到；还要 node-gyp 原生编译（Windows+Docker 雷区）。→ 用 `node:sqlite`
- **靠 `worker.terminate()` 做硬超时**：实测对卡在同步原生调用的 worker 永不 resolve。→ 放弃等待 + 标记污染 + 换新 worker
- **`SQLite immutable=1`**：重 seed 后长连接读脏页。→ `{ readOnly: true }`
- **迁 PostgreSQL 换安全叙事**：`node:sqlite` 的 `setAuthorizer` 已实测可用，比只读角色更硬更便宜。→ 不换

（完整「明确不做」的判断理由见 [需求与验收](01-requirements.md#五明确不做)。本文只补「如果做会怎么做 + 触发条件」。）

# 评测体系

这是整个项目唯一能在简历上写出数字的部分，也是最稀缺的部分 —— 绝大多数 Text-to-SQL 作品集只有一段录屏。

没有评测就无法回答「你怎么知道它准不准」和「你做的优化到底有没有用」。这两个问题会直接把项目打回 demo。

## 一、测试集：30 题，六层各 5 题

| 层级 | 题数 | 考察什么 |
|---|---|---|
| 简单聚合 | 5 | 基础 COUNT / SUM，建立基线 |
| 时间筛选 | 5 | 相对时间解析、跨年跨季度边界 |
| 多表 JOIN | 5 | 连接正确性、扇出陷阱 |
| 分组 TopN | 5 | GROUP BY + ORDER BY + LIMIT |
| 口径陷阱 | 5 | status 过滤、unit_price vs price、COUNT DISTINCT、NULL 处理 |
| **不可答题** | 5 | 拒答校准 |

**不可答题占 5/30 = 16.7%**（满足「不低于 15%」的拒答校准要求），且必须覆盖两种性质完全不同的情况：

- 2 题问数据源里根本不存在的实体（员工工资、库存周转）
- 2 题是口径本质歧义（复购率按自然月还是 90 天窗口、毛利是否扣退款）
- 1 题时间范围完全越界

### 为什么是 30 题而不是 120 题

手写 gold SQL 是全部计划里**被最严重低估的工时** —— 30 题就要 2-3 天纯枯燥劳动，而且是最可能让人在中途崩掉的任务。

六层各 5 题已经足够支撑「分层准确率 + 逐轮优化 + 由对转错清单」的全部叙事。省下的 3-4 天投给优化轮次 —— **简历上那句带数字的话来自优化轮次，不来自题目数量。**

### 冻结纪律

题面在**第 1 周写完**（写题不需要任何代码，却迫使你真正读懂数据），git commit 并打 tag `evalset-frozen-v1`，时间戳早于任何 agent 实现代码的 commit。

> 这是唯一能扛住「你的题是谁出的、什么时候出的」这一问的答案。

## 二、Gold 的建立与自检

每题手写 SQL，执行后把结果 JSON **由脚本落盘**（不手抄）。存两份：gold SQL + 该 SQL 执行出的结果。

三道自检关卡，缺一不可：

1. **金额类题目（≥10 题）用第二种写法交叉验算** —— 两种写法结果不一致就说明至少有一个错了，必须查清
2. **全部 30 条 gold SQL 先过一遍自己的口径规则引擎**，0 条 block 级违规才算定稿
3. **锚点题核对** —— 这三个数字已用脚本核对过：

| 指标 | 正确值 |
|---|---|
| 总销售额（已完成） | 41,015,358.75 |
| 客单价 | 5,057.38 |
| 已完成订单数 | 8,110 |

任何一轮评测里它们对不上，就说明比对链路本身坏了。

> **最难发现的错**：手写 gold SQL 时你同样会漏 `status` 过滤、同样会踩 fan-out。用一套错答案跑出「准确率 92%」，然后所有优化决策都建立在谎言上。这就是为什么标准答案也要过自己的规则引擎。

## 三、打分方法

### 只比执行结果，不比 SQL 文本

同一个问题有无数种正确写法。也**绝不用 LLM-as-judge 判数值对错** —— judge 只允许用于评价结论文字的可读性，且不计入准确率。

### 等价比对器的规则

| 维度 | 规则 |
|---|---|
| 列名 | 不参与比较 |
| 列序 | 无关 |
| 行序 | **仅当 gold SQL 含 `ORDER BY` 时才校验** |
| 浮点 | 容差 0.01 |
| 数值类型 | int 与 decimal 归一 |
| NULL / 0 / 空字符串 | **三者严格判不等** |
| 单值标量 vs 单行单列表格 | 视为等价 |

**比对器本身必须有独立的 Vitest 用例集覆盖上述每一类。**

> 绝不用 `JSON.stringify(a) === JSON.stringify(b)`。它在浮点尾差、列名不同、列序、行序、int/decimal、NULL vs 0 上**全部误判**，而一个静默误判的比对器会让整套准确率变成谎言，后面所有优化决策建立在噪声上。

### 不可答题怎么判

判定标准不是结果比对，而是「系统是否进入拒答态且给出了澄清选项或可查内容清单」。

**系统对不可答题给出了任何数字答案，直接计入自信错答。**

## 四、要记录的指标

每轮全部上报。**任何单独一个数都不算成绩。**

| 指标 | 说明 |
|---|---|
| 总准确率 | |
| 六层分层准确率 | 总分会掩盖此消彼长 |
| 拒答率 | **硬上限 12%，超了这一轮直接判不合格** |
| **自信错答率** | 系统标注「已核验」但结果与 gold 不等价的比例 —— **最重要的一个数** |
| 口径规则误报率 | block 级规则打回了一条本来正确的 SQL 的比例，**超 5% 的规则降级为 warn 或删除** |
| 平均重试次数 | |
| 结构化解析失败率 | 超 3% 说明提示词设计有问题，不是偶发 |
| p50 / p95 端到端延迟 | |
| 单题平均 token 与成本 | |

### 「本轮相对上轮由对转错的题号清单」

这一栏是定向调优时真正用得上的东西。

> 提示词修改有**跷跷板效应**：为修好「时间筛选」类加的一句约束，会让「多表 JOIN」类退化。只看总分，两者相抵会显示「没变化」，于是你误判这次修改无效 —— 而实际上你同时做对了一件事和做错了一件事。

## 五、运行方式：三模式

```
live    真实调用模型
record  真实调用 + 把响应录成 cassette
replay  完全离线，从 cassette 读
```

所有 LLM 请求按 `hash(模型 + 温度等参数 + 规范化后的 messages)` 录制成 `fixtures/llm/*.json` 并提交进 git（设体积上限，定期清理无引用的）。

**一份 cassette，三个用途：**

| 用途 | 价值 |
|---|---|
| CI 回归门禁 | replay 跑全量 30 题，<60 秒、零成本、结果完全确定 |
| 调优期重跑 | 十几轮迭代近乎免费 |
| 无 key 演示 | 面试官不配任何 API key 也能走完整个产品，包括看到重试自愈的全过程 |

> 这是全场性价比最高的设计，而且直接回答「LLM 系统怎么做自动化测试」这个几乎所有面试官都会问、绝大多数候选人答不上来的问题。

### 缓存键的风险

| 键设计 | 后果 |
|---|---|
| 太脆（含无关字段） | 重构后全量失效，录制成本重来 |
| 太糙（漏关键字段） | **提示词改了却复用旧响应 ——「优化后提升」完全是假的** |

对策：`messages` 序列化必须规范化（键排序、去掉无关字段）；**每个里程碑抽 10 题同时跑 live 和 replay 做对齐**，不一致就说明键太糙，必须先修。

### `eval:quick`

10 题子集，90 秒内跑完，供改完提示词立刻自查。

另有按 `(提示词 + 模型 + 参数)` 哈希的**磁盘缓存**，与 cassette 互补 —— cassette 解决 CI 门禁与无 key 演示，磁盘缓存解决日常重跑成本。

## 六、CI 门禁

GitHub Actions 在 replay 模式跑全量 30 题：

- 总准确率相对 main 基线掉 >1 题 → PR fail
- 任何原先通过的题回归 → PR fail
- 结果以 PR 评论形式贴出对比表和由对转错的题号

fork PR 不使用真实 key，只走 cassette。

**先观察一周再开 required check** —— 避免噪声让门禁一开始就被关掉。

## 七、记录与叙事

每轮优化写一条 `docs/eval-log.md`：

```markdown

- 模型：ark-code-latest
- commit：abc1234
- 本轮只改了：低基数列枚举值全量注入

| 层级 | before | after |
|---|---|---|
| 简单聚合 | 5/5 | 5/5 |
| 时间筛选 | 3/5 | 4/5 |
| 多表 JOIN | 3/5 | 3/5 |
| 分组 TopN | 4/5 | 4/5 |
| 口径陷阱 | 1/5 | 3/5 |
| 不可答题 | 4/5 | 4/5 |
| **总准确率** | **66.7%** | **76.7%** |
| 自信错答率 | 23.3% | 13.3% |

| 规则误报率 | 3.3% | 3.3% |

```

### 错题人工归因

每道错题归到四类之一，因为**优化手段是按类别对应的**，不分类就只能瞎调提示词：

1. schema 理解错
2. 业务口径漏
3. 时间边界错
4. 聚合粒度错

分类结果写进 `eval-log.md`。

### 对外呈现

README 里放一张 markdown 表格即可。**不做站内趋势图和热力图** —— 那是零边际价值的 CSS 时间。

## 八、计划中的四轮优化

第 4 周执行，**每轮只改一处并全量重跑**：

1. 低基数列枚举值全量注入
2. 口径规则文本注入提示词
3. SQL 生成后的自检提示
4. few-shot 开 / 关 A/B

每轮都要有 before/after 六个分层数字 + 由对转错清单。目标不是提升幅度多大，而是**能说清每一轮改了什么、为什么有效或无效**。

## 九、明确不做

| 不做 | 理由 |
|---|---|
| 每题跑 3 次取多数 + 上报方差 | 3 倍 token 和 3 倍等待换降噪，作品集不需要这个精度。`temperature=0` + cassette 回放已经给了足够确定性 |
| 扰动数据库反过拟合（P2 保留） | gold 是 SQL 而不是写死的结果，「把答案硬编码进 SQL」本来就不是本项目的失败模式 —— 它防的是一个不存在的敌人。只在第 7-8 周有余量时做 |
| 60/120 题的 dev + test 双集 | 30 题冻结集一套即可，跑冻结集的日期与次数如实记进 eval-log |
| Ragas / DeepEval 等语义相似度指标 | 面向 RAG 的指标，数值正确性只能走执行结果比对 |
| LLM-as-judge 判数值 | 同上 |
